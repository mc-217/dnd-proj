# Sending data to the database

**Start here only after `connectSupabase.md` works.** The check is that this
returns an empty array rather than an error:

```bash
curl http://localhost:3000/api/characters
```

```
[]
```

`[]` means Nest reached Supabase and found an empty `characters` table. In this
lesson you'll put rows into it — first by hand with `curl`, then from the UI —
and learn where the write can fail along the way.

Keep the backend running in one terminal (`cd backend && pnpm start:dev`) and
use a second terminal for the commands below.

---

## The path a write takes

Nothing here talks to Postgres directly. Every write makes six hops, and
knowing them is what lets you debug quickly:

| # | Where | What it does |
| --- | --- | --- |
| 1 | `character-create/src/components/character-summary.tsx` | `saveCharacter()` POSTs JSON to `/api/characters` |
| 2 | `backend/src/characters/characters.controller.ts` | `@Post()` receives the body as `CreateCharacterDto` |
| 3 | `backend/src/characters/characters.service.ts` | `create()` fills in defaults (`level ?? 1`, `background ?? null`) |
| 4 | `backend/src/characters/supabase.service.ts` | `insertOne()` POSTs to `<url>/rest/v1/characters` |
| 5 | Supabase / PostgREST | translates it to SQL; constraints are enforced here |
| 6 | back up the chain | `mapRow()` converts `null` to `undefined`, and the row is returned as JSON |

The important consequence of hop 5: **the database is the last line of defence,
and right now it's the only one.** More on that in Step 5.

## Step 1 — Insert your first row with `curl`

```bash
curl -i -X POST http://localhost:3000/api/characters \
  -H "Content-Type: application/json" \
  -d '{"name":"Bruenor","race":"dwarf","class":"fighter","level":3}'
```

What the flags do:

- `-i` prints the response status line and headers. Use it while learning.
- `-X POST` sets the method; without it `curl` sends a GET.
- `-H "Content-Type: application/json"` tells Nest to parse the body as JSON.
  Leave it off and `@Body()` arrives empty.
- `-d` is the body itself. Single quotes on the outside, double quotes inside,
  because JSON requires double quotes.

You should get `HTTP/1.1 201 Created` and a body like:

```json
{"id":"3f8c...","name":"Bruenor","race":"dwarf","class":"fighter","level":3}
```

Three things to notice:

- **The `id` was generated by Postgres**, not by your app — that's the
  `gen_random_uuid()` default from `schema.sql`.
- **201, not 200.** Nest returns 201 for `@Post()` by default.
- **No `created_at` in the response**, even though the column exists and was
  populated. `mapRow()` only copies the fields declared on the `Character`
  interface. The database has more than the API exposes, which is fine — but
  it's why you can't read the timestamp from the API yet.

`level` and `background` are optional. This is also valid:

```bash
curl -X POST http://localhost:3000/api/characters \
  -H "Content-Type: application/json" \
  -d '{"name":"Nameless","race":"human","class":"rogue"}'
```

The service fills in `level: 1`, and `background` becomes SQL `NULL`.

## Step 2 — Confirm the row really landed

Don't take the API's word for it. Open the Supabase dashboard →
**Table Editor** → `characters`. Your rows should be there, with `created_at`
filled in.

Or run this in the **SQL Editor**:

```sql
select id, name, class, level, created_at
from public.characters
order by created_at desc;
```

Seeing the row in the dashboard proves the whole chain end to end. If the API
returned 201 but the table is empty, you are pointed at a different project
than the one you're looking at — recheck `SUPABASE_URL` in `backend/.env`.

## Step 3 — Read it back

```bash
curl http://localhost:3000/api/characters
```

You'll get an array, newest first — that ordering comes from
`order=created_at.desc.nullslast` in `selectAll()`.

## Step 4 — Update and delete

Update sends only the fields you want changed:

```bash
curl -X PATCH http://localhost:3000/api/characters/<id> \
  -H "Content-Type: application/json" \
  -d '{"level":4}'
```

`PATCH` is deliberate, not `PUT` — `UpdateCharacterDto` has every field
optional, so a partial body is the whole point.

Delete returns no body at all:

```bash
curl -i -X DELETE http://localhost:3000/api/characters/<id>
```

Expect `HTTP/1.1 204 No Content`. That's set explicitly with
`@HttpCode(HttpStatus.NO_CONTENT)` on the controller method. An empty response
to a successful delete is normal and not an error.

## Step 5 — The validation gap (the real lesson)

Try sending something invalid:

```bash
v
```

You get **500 Internal Server Error**, and the response body quotes Postgres
directly, because `SupabaseService.request()` wraps the failure detail in the
exception it throws:

```json
{"statusCode":500,"message":"Supabase request failed (400): {...characters_class_check...}"}
```

Note that PostgREST itself answered **400** — the correct code — and your
backend upgraded it to a 500 on the way out.

That 500 is wrong, and understanding why is the most valuable thing in this
lesson. The client sent bad data, so this should be a **400 Bad Request** — a
500 means "the server broke," which invites the caller to retry a request that
can never succeed.

The reason is that `CreateCharacterDto` is only a TypeScript type:

```ts
export class CreateCharacterDto {
  name!: string;
  race!: string;
  class!: CharacterClass;
}
```

Types vanish at compile time. `main.ts` installs no `ValidationPipe`, so at
runtime Nest hands your service whatever JSON arrived — wrong types, missing
fields, extra fields, anything. Prove it:

```bash
curl -i -X POST http://localhost:3000/api/characters \
  -H "Content-Type: application/json" \
  -d '{"name":"Ghost"}'
```

That reaches Postgres too, and fails there on `race` being `NOT NULL`.

So today your `CHECK` constraints and `NOT NULL` columns are doing all the
validation. That's a decent safety net — it's why `schema.sql` bothers with
constraints — but the errors surface as 500s instead of useful messages.
Exercise 1 fixes it.

## Step 6 — Save from the UI

The frontend already has this wired up. `CharacterSummary` has a
**"Save to backend"** button that POSTs to `${apiBaseUrl}/characters`.

The backend occupies port 3000, so start Next on a different port:

```bash
cd character-create
pnpm dev -p 3001
```

Open <http://localhost:3001>, pick a race and a class, then save. Cross-origin
requests work because `main.ts` calls `app.enableCors()`.

Two details worth reading in `character-summary.tsx`:

- It lowercases the class (`character.characterClass.toLowerCase()`) because
  the `CHECK` constraint only accepts lowercase values. Any class in the UI
  that isn't in that list of twelve will fail at the database.
- It never sends `level`, so every character saved from the UI is level 1 —
  the service default. Exercise 4.

The button stays disabled until both race and class are chosen, which is
client-side validation doing the job the server should also be doing.

## Troubleshooting writes

| Symptom | Cause |
| --- | --- |
| 500, log mentions `characters_class_check` | Class value isn't one of the twelve lowercase names |
| 500, log mentions `null value in column` | A `NOT NULL` field was missing from the body |
| 500, log mentions `invalid input syntax for type uuid` | The `id` in your URL isn't a UUID |
| 400 from Nest before your code runs | Malformed JSON — usually a quoting mistake in `-d` |
| Body arrives empty | Missing `Content-Type: application/json` |
| 404 on a real id | Right id, wrong project or table |
| 201 but nothing in the dashboard | `SUPABASE_URL` points at a different project |
| Browser console shows a CORS error | Backend restarted without `enableCors()`, or wrong port |

There are two different flavours of 500, and telling them apart saves time:

- **A descriptive one** — `"Supabase request failed (400): ..."`. Supabase was
  reached and rejected the data. `SupabaseService` threw this deliberately, so
  the reason is right there in the response body.
- **A bare one** — `{"statusCode":500,"message":"Internal server error"}`. An
  unexpected exception escaped, such as `fetch` failing on an unresolvable
  `SUPABASE_URL`. Nest hides these on purpose, so the only place the cause
  appears is the backend terminal.

Either way the backend log has the full stack trace; the response body only
sometimes does.

## Exercises

### 1. Turn bad input into a 400 instead of a 500

The main event. Install `class-validator` and `class-transformer`, add
decorators to `CreateCharacterDto` (`@IsString()`, `@IsIn([...])`,
`@IsOptional()`, `@IsInt()`, `@Min(1)`, `@Max(20)`), and register a global
`ValidationPipe` in `main.ts`.

Use `whitelist: true` so unexpected fields are stripped rather than forwarded.

Verify: the `"wizrd"` request from Step 5 should now return 400 with a message
naming the bad field, and never reach Supabase.

### 2. Translate database errors into honest status codes

Even with Exercise 1 done, some failures can only be detected by Postgres — a
unique violation, for example. In `SupabaseService.request()`, inspect the
PostgREST error code and throw the right Nest exception: `409 Conflict` for a
unique violation, `400` for a check violation, 500 only for genuine surprises.

### 3. Let the user type a name

Right now the UI generates `"<race> <class> Adventurer"`. Add a controlled text
input, store it in the character context, and send it. Decide what should
happen when it's blank.

### 4. Send `level` from the UI

The API accepts it and the UI never sends it. Add a level control, then confirm
with `curl` that the value round-trips.

### 5. Expose `created_at` through the API

Add it to the `Character` interface, copy it in `mapRow()`, and display "saved
at" in the UI. Notice you don't need a migration — the column already exists.

### 6. Build a saved-characters list page

A new route that GETs `/api/characters` and renders the rows in a table.
`@tanstack/react-query` is already a dependency; use it and you get caching and
refetch-after-save almost for free.

### 7. Add delete to the UI

Wire a delete button to `DELETE /api/characters/:id`. Remember the 204 has no
body, so don't call `response.json()` on it — a mistake that throws a confusing
parse error.

### 8. Handle the double-click

The save button disables itself while saving, but nothing stops two rapid
submissions from creating two rows. Add the `UNIQUE (user_id, name)` constraint
from `practice.md` exercise 8 and handle the resulting conflict, or debounce it
on the client. Consider which layer should really own this.
